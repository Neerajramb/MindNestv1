1. Purpose & Vision

This document consolidates the Project Requirements Specification, Software Requirements Specification, System Design & Architecture, Database Design, API Specification, UI/UX Design, and Use Case/Test Specification into a single reference. It establishes the agreed functional scope, actors, architecture, data model, API surface, screen flows, and verification plan for the proposed multimodal assistive application, frozen before detailed implementation.

Vision: A unified assistive platform supporting people with Mild Cognitive Impairment through memory assistance, routine management, familiar-person recognition, object-location assistance, contextual conversation retrieval, safety monitoring, and caregiver support — reducing dependence on multiple disconnected apps via a privacy-preserving multimodal companion. Smartphone capture (audio, video, GPS) is paired with heavier AI processing on a secondary/local node.

Product perspective: A multimodal assistive application rather than a standalone chatbot — it accepts camera, audio and location input, routes it through specialized modules, stores relevant structured/unstructured data, and returns context-aware assistance.

2. Scope

2.1 In Scope

  • Patient mobile application with a simple, accessible interface
  • Caregiver interface/dashboard for patient management and monitoring
  • Object detection, tracking and last-observed object-location retrieval
  • Facial detection and recognition of registered/familiar individuals
  • Contextual conversational memory via STT, embeddings, retrieval and an LLM/RAG layer
  • Personal AI assistant accessing structured application data and retrieved memories
  • Daily schedule, calendar/appointments and reminder management
  • Medication schedule and medication reminders
  • GPS-based geofencing and caregiver alerts
  • Relaxation, meditation and therapeutic/well-being audio features
  • Notifications and activity/event logging
  • Privacy, authentication, authorization and controlled access to sensitive data

2.2 Out of Scope for the Baseline

  • Medical diagnosis or clinical decision-making
  • Automatic prescription, dosage modification or medication changes by AI
  • Claiming physical ingestion of medication unless an actual verification mechanism is implemented
  • Guaranteed current physical location of an object — the system reports a last detected/observed location
  • Identity claims for unregistered people when recognition confidence is insufficient
  • Predictive health analytics, smart-home/IoT/wearables integration and secure cloud sync as mandatory baseline features (future scope)

3. Stakeholders and Actors

Actor Role Primary Needs
Patient Primary end user Simple assistance, reminders, memory cues, object finding, familiar-person recognition, schedule and conversational support
Caregiver Remote support and configuration Patient status, schedules, medications, safe zones, alerts, familiar-person registration, activity information
AI/Backend System Processing layer Receive multimodal input, run AI services, retrieve data, generate responses, trigger actions
Notification Service Delivery mechanism Deliver reminders, alerts and emergency notifications

3.1 User Characteristics

  • Patient — needs simple, low-cognitive-load interaction, clear feedback, optional voice assistance and minimal navigation.
  • Caregiver — needs detailed configuration, monitoring, notifications and management controls.

3.2 Operating Environment

  • Android/iOS smartphone or supported mobile device for patient-side capture and interaction
  • Backend server/local processing node for APIs and AI services
  • Camera and microphone for multimodal capture
  • Location services/GPS for geofencing
  • Database and vector storage for structured records and memory retrieval

4. System Architecture

4.1 Architecture Goals

  • Keep patient interaction simple while hiding technical complexity
  • Separate AI modules so they can be developed and tested independently
  • Keep sensitive processing/storage under controlled infrastructure where feasible
  • Use structured databases for deterministic information and vector retrieval for unstructured memory
  • Allow the system to continue core schedule/reminder functions even when a non-critical AI service fails

4.2 High-Level Architecture (Logical Layers)

Layer Components Responsibility
Presentation Patient Mobile App; Caregiver Dashboard User interaction, camera/microphone/location permissions, visual/voice output
API/Application Django/REST backend; Authentication; RBAC; Decision/Orchestration Business rules, API endpoints, access control, coordination
AI Services Object Detection/Tracking; Face Recognition; STT; Embeddings; RAG; LLM; optional emotion analysis Specialized inference and contextual assistance
Data Relational DB; Vector Store; Object/Face metadata; Logs Persistent structured data, searchable memories and audit information

4.3 Logical Data Flow

The mobile application captures multimodal data and sends it to a Django backend. The backend routes data to OpenCV/computer-vision, NLP/RAG and face-recognition components, then combines results through a decision engine before delivering patient assistance or caregiver dashboard information.

  1. Patient action/input → Mobile app
  2. Mobile app → authenticated backend API
  3. Backend → appropriate AI/business service
  4. AI service → structured result or retrieval context
  5. Decision/orchestration layer → final action
  6. Patient receives assistance; caregiver receives monitoring/alert output where applicable

4.5 Object Intelligence Pipeline

Camera input → frame extraction → object detection → object tracking → scene/context understanding → object observation storage → patient query → last-observation retrieval → text/voice response.

Stored observation fields: object_id (category/instance), timestamp, location/context (room/scene label), confidence (detection score), source (camera/session).

4.6 Face Recognition Pipeline

Camera input → face detection → face embedding → registered-person matching → identity/relationship cue → optional RAG context enrichment.

The system must distinguish recognition from identification confidence — unknown/low-confidence faces are never force-mapped to a registered person.

4.7 Conversational RAG Pipeline

Microphone/text input → speech-to-text (if required) → conversation cleaning/segmentation → context extraction (person/topic/time) → embedding generation → vector search → metadata filtering/reranking → prompt/context construction → LLM response generation → text/voice response.

Hybrid retrieval strategy: deterministic retrieval for structured data, semantic retrieval for memory. E.g. "What medicine do I take at 8 AM?" queries the medication/schedule tables; "What did my daughter tell me last Sunday?" uses conversational memory retrieval, optionally filtered by recognized person and time context.

4.8 Geofencing Pipeline

  1. Caregiver defines a named safe zone with center and radius
  2. Location updates received from the mobile device when permission/service is available
  3. Backend or device-side safety service evaluates the point against the configured boundary
  4. On violation, an alert record is created
  5. Notification service delivers the alert to the caregiver
  6. System logs the event

4.9 Failure Isolation

Failure Core System Behavior
Object AI down Schedules, reminders and caregiver management continue
Face AI down Identity cue unavailable; other assistant functions continue
RAG/LLM down Structured schedule/medication queries continue; assistant reports limited capability
GPS unavailable Geofence status becomes unavailable/limited; system records condition
Notification provider down Pending notification is persisted/retried where supported

6. Non-Functional Requirements

ID Requirement Priority Acceptance / Verification
NFR-001 Privacy High Sensitive audio, video, face, conversation and location data shall be protected and minimized
NFR-002 Security High Authenticated access, role-based authorization and secure transport/storage shall be used
NFR-003 Usability High Patient interface uses simple navigation, clear labels, large touch targets and optional voice interaction
NFR-004 Performance High Normal interactions return within a practical interactive delay; AI latency measured during testing
NFR-005 Reliability High Failure of one non-critical AI module shall not crash the entire application
NFR-006 Maintainability Medium AI modules and backend services shall be modular and independently testable
NFR-007 Scalability Medium Architecture allows additional patients and modules without redesigning the entire system
NFR-008 Auditability Medium Important configuration changes and alerts shall be timestamped and logged

Additional detail from the SRS: - Security — protect authentication credentials, restrict data by role, secure API communication, protect sensitive patient data. - Privacy — raw audio/video and location data not retained longer than required by the defined feature; sensitive data accessible only to authorized users. - Performance — AI pipelines benchmarked for latency on target hardware; targets recorded after prototype measurement rather than assumed. - Reliability — a failure in one AI component should degrade that feature gracefully rather than bring down core scheduling/reminder functions. - Maintainability — modules have clear service boundaries and interfaces; model implementations replaceable without rewriting unrelated modules. - Safety — AI-generated information shall be grounded in stored data and communicate uncertainty where relevant.

7. Business Rules & Error Handling

7.1 Business Rules

  • BR-01: A patient may have one or more authorized caregivers according to the application's permission model
  • BR-02: A familiar-person profile must exist before the system can reliably identify that person
  • BR-03: An object answer refers to the latest valid observation, not a guaranteed current location
  • BR-04: A low-confidence face match must not be presented as a confirmed identity
  • BR-05: Structured data such as medication schedules should be retrieved directly from the database rather than invented by the LLM
  • BR-06: RAG responses should be grounded in retrieved memories and indicate lack of information when appropriate
  • BR-07: Geofence alerts depend on location service availability and configured rules
  • BR-08: AI assistance is supportive and does not replace clinical judgment or emergency services

7.2 Error & Exception Handling

Scenario Expected Behavior
Camera unavailable Explain that camera access is unavailable and allow non-camera features to continue
Microphone unavailable Allow typed interaction and display a clear voice-input error
No object detected State that the object could not be located from available observations
Face confidence too low Identify as unknown / ask user to try again; do not guess
No relevant memory State that no relevant stored memory was found
LLM unavailable Fallback to structured responses for schedules/reminders where possible
GPS unavailable Disable/flag geofence monitoring and notify caregiver if configured
Notification service unavailable Persist pending notification state and retry where supported

7.3 Security & Privacy Requirements

  • Use authenticated sessions and role-based authorization
  • Protect face embeddings and conversation data as sensitive information
  • Use secure transport between mobile and backend
  • Store only data required for project functionality
  • Provide caregiver access only to authorized patient records
  • Record important administrative/security events
  • Do not expose internal prompts, embeddings or raw sensitive data unnecessarily

7.4 Verification Strategy

  • Inspection — documentation/UI/configuration review
  • Functional test — execute a defined input and compare output
  • Integration test — verify interaction between modules
  • Performance test — measure latency/resource usage
  • Security test — verify authorization and access boundaries

8. Database Design & ER Model

8.1 Design Principles

  • Use a relational database for users, patients, schedules, medications, appointments, reminders, alerts and configuration
  • Use a vector index/store for conversation/object/person memory embeddings; keep a relational metadata record for every vectorized item
  • Use foreign keys to enforce patient ownership and caregiver relationships
  • Use timestamps consistently for observations, conversations, reminders, locations and alerts
  • Do not store raw biometric media unless required; store controlled recognition representations and metadata
  • Treat last-seen object information as an observation record, not a guaranteed current state

8.5 Indexing Strategy

  • users.email — unique index
  • caregiver_patient(caregiver_id, patient_id) — composite unique/index
  • object_observations(object_id, observed_at DESC) — fast last-seen retrieval
  • conversations(patient_id, started_at DESC)
  • memories(patient_id, event_time DESC)
  • memories(patient_id, recognized_person_id) — person-aware retrieval metadata
  • medication_schedules(medication_id, time_of_day)
  • reminders(patient_id, scheduled_at, status)
  • locations(patient_id, recorded_at DESC)
  • alerts(patient_id, created_at DESC, acknowledged_at)
  • activity_logs(patient_id, created_at DESC)

8.6 Data Retention and Privacy Rules

  • Raw camera frames should not be persisted by default unless required for a defined feature
  • Raw audio should not be persisted by default; transcripts retained only per project retention policy
  • Face embeddings require controlled access and should be deletable when a familiar-person profile is revoked
  • Location history should have a defined retention window; avoid indefinite tracking by default
  • Conversation memory should have an explicit retention status and deletion path
  • Caregiver access must always be checked against caregiver_patient authorization

8.7 Implementation Notes

The schema is database-agnostic at the logical level. A Django implementation can map these entities to Django models and migrations. UUIDs are recommended where practical. JSON fields may be used for flexible metadata, but core business fields should remain typed relational columns.

9.15 Security Requirements for APIs

  • Every protected endpoint must perform authentication
  • Every patient-specific endpoint must enforce patient/caregiver authorization
  • Do not trust client-supplied patient_id without authorization checks
  • Do not expose raw face embeddings to ordinary clients
  • Do not expose internal vector-store identifiers unless needed
  • Validate uploaded media type and size
  • Apply rate limits to authentication, face recognition and assistant endpoints where practical
  • Log security-sensitive actions without logging unnecessary sensitive content

9.16 API Dependency Flow

  1. Mobile app authenticates → receives access token
  2. Mobile app requests schedule/medication → backend queries relational database
  3. Camera frame → object/face service → backend stores result
  4. Conversation → STT → memory ingestion → embedding/vector store
  5. Assistant query → intent/context routing → structured DB and/or vector search → LLM → response
  6. GPS event → geofence evaluator → alert record → notification

10. UI/UX Design & Screen Flow

10.1 UX Principles

  • Keep the number of choices visible at one time low
  • Use large touch targets, clear labels and consistent iconography
  • Prefer plain language over technical terminology
  • Use persistent access to the most important functions: Assistant, Reminders, Schedule and Help
  • Make important information visible without requiring deep navigation
  • Never make a recognition result look more certain than it actually is
  • Use confirmation for potentially consequential caregiver actions
  • Provide obvious recovery paths when AI recognition or connectivity fails
  • Maintain the same terminology throughout the patient and caregiver experiences

Home (P-02) should answer three questions immediately: "What do I need to do?", "What is next?", and "Can I ask for help?" — elements: greeting, current time/date, next reminder, today's schedule, Assistant button (primary), Find-an-object shortcut, Who-is-this shortcut, Well-being shortcut, optional compact safety-state indicator.

AI Assistant (P-03) — text and (if implemented) voice input; context = current patient, recent schedule/reminders, recognized person, object observations, permitted memories; short direct answer first with optional supporting context; states uncertainty rather than inventing an answer; supports follow-up without restarting the session. Quick prompts: "Where are my keys?", "Who is this?", "What do I have today?", "When is my appointment?"

Person Recognition Flow: open "Who is this?" or camera detects a face → capture frame → face detection → recognition compared against registered people → match above threshold shows name/relationship → no reliable match shows "I'm not sure who this is" → recognized person's permitted memory can inform the conversation.

Object Finder Flow: select "Find an object" or ask the assistant → identify requested object → retrieve latest observation → display last detected location/time/confidence/context → no observation shows "I don't have a recent location for that item" → never presents an old observation as guaranteed current location.

Reminder Flow states: Upcoming (card with time/action) → Due now (prominent notification) → Acknowledged (marked complete) → Snoozed (shows next reminder time) → Missed (clearly marked; caregiver notification may trigger per configuration).

Schedule & Calendar Flow: default view opens to today; upcoming event visually emphasized; completed items remain visible but secondary; appointments show time/title/location; medication events visually distinguishable.

Well-being (P-12): meditation (selectable guided session with duration), therapeutic tones (selectable audio/tonal content), session state (play/pause/stop), completion recorded only if user chooses or requirements define automatic recording; content is supportive, never a substitute for professional treatment.

11.2 Detailed Use Cases

UC-06 Find Misplaced Object 1. Patient selects or speaks the name of an object 2. System searches recent object observations 3. If a valid observation exists, the latest is selected 4. System presents object name, last observed context/location and timestamp 5. If no observation exists, system states it has no recorded observation

UC-07 Recognize Familiar Person 1. Camera captures a face 2. System detects the face 3. System creates a recognition representation 4. Representation is compared with registered familiar people 5. If confidence exceeds threshold, name and relationship are displayed 6. Otherwise the person is treated as unknown

UC-08 Retrieve Conversation Memory 1. Patient asks a memory-related question 2. System converts voice to text when required 3. System extracts available person/topic/time context 4. System retrieves relevant vector memories 5. Relevant memory is passed to the response generator 6. System produces a contextual answer and avoids unsupported claims

UC-11 Handle Geofence Violation 1. Caregiver has an active safe zone 2. Patient device provides a supported location update 3. System evaluates location against the safe zone 4. If outside, a violation event is created 5. Caregiver notification is generated 6. Event is recorded in activity/alert history

11.3 Demonstration Scenarios

  • A — Lost object: Patient asks for keys; system retrieves the latest observation and speaks/displays the result
  • B — Familiar person: Patient points camera at a registered person; system identifies name/relationship
  • C — Contextual memory: Recognized person is associated with a query; system retrieves the relevant previous conversation
  • D — Routine: Patient sees today's schedule and receives a medication reminder
  • E — Safety: Test patient location leaves the safe zone; caregiver receives an alert
  • F — Caregiver management: Caregiver updates medication/schedule and sees the updated status

14. Constraints & Assumptions

  • The project is intended as a college software project and must remain implementable within the available development time and hardware
  • AI performance will depend on the smartphone camera, lighting, microphone quality, model choice and available compute
  • Continuous camera/audio/GPS processing can have battery and privacy implications
  • Geofencing accuracy depends on device location services and environmental conditions
  • RAG quality depends on the quality and amount of stored conversation/event information
  • External cloud AI services should not be treated as mandatory — the project emphasizes privacy-preserving/local processing

Source basis: the requirements baseline is based on the team's handwritten project feature list and the supplied 19-page project presentation, which describes the problem, six objectives, object-tracking pipeline, conversational RAG pipeline, face recognition/geofencing pipeline, data-flow architecture, technology stack, privacy-first architecture and future scope.
